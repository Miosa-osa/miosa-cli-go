# miosa command reference

Generated by `miosa __docs`; do not edit by hand.
Regenerate with `make docs`.

## Global flags

- `--api-key string` - API key (overrides MIOSA_API_KEY and config).
- `--api-url string` - API base URL (overrides MIOSA_BASE_URL and config).
- `--bill-to string` - Organization a new machine bills: id, slug or name (env MIOSA_BILL_TO).
- `--json` - Print machine-readable JSON (same as --output json).
- `--no-update-notice` - Silence the new-version notice (env: MIOSA_NO_UPDATE_NOTICE=1).
- `--org string` - Organization to work in: id, slug or name; refused if this key does not act in it (env MIOSA_ORG).
- `-o, --output string` - Output format: text or json. (default `text`)
- `--profile string` - Config profile to use (env: MIOSA_PROFILE).
- `-q, --quiet` - Suppress informational output.
- `--retries int` - Retries on 429 and transient 5xx errors (default 3, env: MIOSA_RETRIES). (default `-1`)
- `--timeout int` - Request timeout in seconds (0 = no timeout); for exec and ssh also the command timeout, 1-300. (default `60`)

### `miosa admin`

Platform administration (platform operators only).

```
miosa admin
```

Platform administration.

These commands operate on platform state, not on your own sandboxes, and they
require a platform operator API key.

#### `miosa admin slot-revocations`

Revoke a producer bake revision (bad-bake protection).

```
miosa admin slot-revocations
```

Manage the revoked producer bake revisions.

A revocation is the supported replacement for a manual sweep after a bad bake.
Every compute host refuses to acquire or warm-claim a slot whose manifest
names a revoked revision, and the reaper retires the idle slots cut from it.
A revocation reaches running hosts within about a minute, without a restart.

Aliases: `slot-revocation`.

##### `miosa admin slot-revocations list`

List every revoked producer bake revision.

```
miosa admin slot-revocations list
```

List every revoked producer bake revision, newest first.

```
  miosa admin slot-revocations list
  miosa admin slot-revocations list --json | jq -r '.data[].revision'
```

Aliases: `ls`.

##### `miosa admin slot-revocations revoke`

Revoke a producer bake revision.

```
miosa admin slot-revocations revoke <revision> [flags]
```

Revoke a producer bake revision.

Take the revision from the manifest of the bad bake (producer.vcs_revision), or
from the blocklist of the bake that produced it.
Revoking is immediate and
idempotent: revoking an already-revoked revision reports already_revoked rather
than failing.

```
  miosa admin slot-revocations revoke 1a2b3c4d --reason "mmds token absent"
```

Aliases: `add`.

Flags:

- `--reason string` - Why the revision is revoked (recorded in the audit trail).

### `miosa agent`

Define, version and run agents.

```
miosa agent
```

An agent is a saved, versioned definition: harness, model, instructions, the
machine it runs on, and what it may do.
Runs always use your own model
connections ('miosa connections add models'). <agent> is a name or an id.

```
  miosa agent new reviewer --harness claude-code --instructions-file review.md
  miosa agent publish reviewer --file config.yaml
  miosa agent diff reviewer 2 3
  miosa agent run reviewer "review PR 42" --sandbox my-box
  miosa agent harnesses
```

Aliases: `agents`.

#### `miosa agent publish`

Publish a new immutable version.

```
miosa agent publish <agent> [flags]
```

Publish a new version of an agent from --file and/or flags.
The full configuration
is validated and fingerprinted; a version never changes after publication, so
a run can always prove what it ran.
Runs started before keep their version.

Flags:

- `-f, --file string` - Configuration as YAML or JSON (the version's `configuration` object).
- `--harness string` - Harness: claude-code, codex, osa or custom.
- `--instructions string` - Instructions text.
- `--instructions-file string` - Read the instructions from a file.
- `--model string` - Model.
- `--overdrive` - Run the harness without approval prompts (stored on the version).
- `--timeout-sec int` - Run time limit in seconds (execution.timeout_seconds).

### `miosa api`

Make an authenticated API request.

```
miosa api [METHOD] <path> [flags]
```

Send a request to the MIOSA API with your stored credentials and print the
response body.
The path is relative to the API base URL (/api/v1).
Use it for
anything the CLI has no command for yet.

The method defaults to GET, or POST when --data is given. --data takes a JSON
string, @file to read a file, or - to read standard input.
A failing status
exits non-zero (see 'miosa --help' for exit codes) and still prints the body.

```
  miosa api /credits/balance
  miosa api GET /sandboxes/my-box/ports
  miosa api POST /webhooks -d '{"url":"https://example.com/hook","events":["sandbox.ready"]}'
  miosa api PATCH /sandboxes/my-box/tags -d @tags.json
  echo '{"name":"x"}' | miosa api POST /workspaces -d -
```

Flags:

- `-d, --data string` - Request body: JSON, @file, or - for stdin.
- `-H, --header stringArray` - Extra header, 'Name: value' (repeatable).
- `-i, --include` - Print the status line and response headers first.
- `-X, --method string` - HTTP method (default GET, or POST with --data).

### `miosa api-key`

Create and manage API keys.

```
miosa api-key
```

API keys let scripts, CI and other programs call MIOSA.
A key is shown once, at
creation and rotation; store it right away.
A key acts as your organization
with the permissions you give it.

```
  miosa api-key create ci --preset ci --expires-in 90
  miosa api-key create reviewer --scope agents:read --scope agents:run
  miosa api-key list
  miosa api-key rotate <id>
  miosa api-key rm <id>

```
The key goes to standard output on create, so you can capture it:
```
  KEY=$(miosa api-key create ci --preset ci --quiet-key)
```

Aliases: `api-keys`, `keys`.

#### `miosa api-key create`

Create a key.

```
miosa api-key create <name> [flags]
```

Create an API key.
With no --scope or --preset the key gets the default set of
scopes.
Presets: read-only (every :read scope), ci (sandboxes, deployments,
previews), agent (run agents on sandboxes), cli (what the miosa CLI uses day to
day, including connections). 'miosa api-key presets' lists them.
Scope names look like sandboxes:exec
or agents:run; see 'miosa api-key list --json' for what existing keys hold.

The secret is printed once. --quiet-key prints only the secret.

Flags:

- `--allowed-ip stringArray` - Only accept requests from this IP or CIDR (repeatable).
- `--expires-in int` - Expire after this many days (default: never).
- `--preset string` - Permission preset: read-only, ci, agent or cli.
- `--quiet-key` - Print only the secret.
- `--rate-limit int` - Requests per minute for this key.
- `--scope stringArray` - A scope to grant, for example sandboxes:exec (repeatable).
- `--workspace-id string` - Bind the key to one workspace.

### `miosa batch`

Create many sandboxes in one request.

```
miosa batch
```

A batch asks for N identical sandboxes and creates them with bounded
concurrency.
The call returns at once with a batch id; 'status' and 'watch'
show how many are up, and 'items' lists the sandboxes.
Quota, credit and
placement apply to every sandbox as for a single 'miosa create'.

```
  miosa batch new --count 50 --size small --name-prefix ci --wait
  miosa batch status <batch>
  miosa batch items <batch>
  miosa batch cancel <batch>
```

Aliases: `batches`.

#### `miosa batch cancel`

Stop creating the sandboxes still pending.

```
miosa batch cancel <batch>
```

Sandboxes already created are left alone; destroy them with 'miosa destroy'.
A batch that has finished cannot be canceled.

#### `miosa batch items`

List the sandboxes of a batch.

```
miosa batch items <batch> [flags]
```

Flags:

- `--limit int` - How many to show.

#### `miosa batch new`

Create a batch of identical sandboxes.

```
miosa batch new [flags]
```

Creates --count sandboxes (1 or more; the server states the maximum for your
plan) with at most --concurrency creating at once.
Prints the batch id.
With --wait the command blocks until the batch has settled and exits non-zero
if any sandbox failed.

```
  miosa batch new --count 20 --template nextjs --name-prefix demo --ttl 2h --wait
```

Flags:

- `--concurrency int` - How many to create at once (default: the server's).

### `miosa connections`

```
miosa connections
```

Connections are what your agents and machines use to reach the outside world:
model providers (Claude, ChatGPT, API keys), apps (GitHub, Slack, Linear,
Discord) and tool servers.
MIOSA's own model keys never power your agents;
every run uses a connection of yours.

```
  miosa connections list
  miosa connections add models anthropic --key-stdin <<< "$ANTHROPIC_API_KEY"
  miosa connections add models claude --sandbox my-box     # sign in with a subscription
  miosa connections add apps github
  miosa connections add tools --name docs --url https://mcp.example.com/sse
  miosa connections rm models anthropic

```

anyone to the console.
Every command takes --external-user (your own id for the
user) and --workspace-id:

```
  miosa connections add models claude --external-user cus_123 --no-wait   # link + code to show them
  miosa connections add models anthropic --external-user cus_123 --key-stdin <<< "$KEY"
  miosa connections test models anthropic --external-user cus_123
  miosa connections tool-keys set APIFY_TOKEN --external-user cus_123 --key-stdin <<< "$TOKEN"
  miosa connections harnesses --external-user cus_123

```
An API key needs the connections:read scope to list and connections:write to
change them: 'miosa api-key create NAME --preset cli' has both.
A list the key
may not read is reported as unavailable instead of failing the whole command.
Signing in with a subscription or an app prints a link or code to finish in a
browser.

Connect a model provider.

```
miosa connections add models <provider> [flags]
```

...): the key is read from standard input (--key-stdin) or typed hidden.
It is

- `--env stringArray` - Environment variable KEY=VALUE (repeatable).
- `--force` - Upload even when the files match the latest version.
- `--forge string` - Deploy this Forge repository (id, org/name or name); builds --branch and redeploys on every push.

- `--root-directory string` - With --forge: the app's directory inside the repository.

#### `miosa deploy push`

Upload a new version to an existing deployment.

```
miosa deploy push <deployment> [flags]
```

Push a new version of a local directory to an existing deployment.

```
  miosa deploy push my-site --dir ./dist
  miosa deploy push lunivate.com            # a hostname works too

```
The deployment keeps its id, URL and domains; only a new version is released.

Flags:

- `--wait-timeout duration` - How long --wait may take. (default `10m0s`)

### `miosa env`

### `miosa exec`

### `miosa prompt`

Run an agent on a sandbox or computer and follow it.

```
miosa prompt [text...] [flags]
```

Send an instruction to a coding agent running in a sandbox or computer, stream
what it does, and print its answer.
Harnesses: Claude Code, Codex, OSA, OpenCode,
pi, Prime Agent, Kimi Code, Mistral Vibe and Hermes Agent (the list is read from
the platform, so a new one works without upgrading the CLI).

The run uses YOUR model connection: add one with 'miosa connections add models'.
One connected plan or key powers every harness that accepts it: see which with
'miosa connections harnesses', and choose which connection a harness uses with
'miosa connections use'.
MIOSA never falls back to its own keys; without a
connection the run is refused.

The target is --sandbox/--computer, the current sandbox ('miosa use'), or a new
machine MIOSA provisions for the run with --new-machine.
The prompt is the
arguments, "-" for standard input, or --file.

Follow-ups: --chat ID names a chat and continues it (the agent keeps its memory
on the machine); --continue resumes the machine's most recent run; --new-chat
starts a chat and prints its id.

```
  miosa prompt "add a health check to the api" --sandbox my-box
  miosa prompt --harness codex --model gpt-6.1-sol "fix the failing test"
  miosa prompt --harness opencode "add a health check"   # on your ChatGPT plan or any key it accepts
  miosa prompt --new-machine --workspace acme "write a README for this repo"
  miosa prompt --chat 3f0c... "now add tests"
  git diff | miosa prompt --sandbox my-box -     # the diff is the prompt
  miosa prompt --agent reviewer --no-follow "review PR 42"   # prints the run id
```

Flags:

- `--after-run string` - What happens to a new machine when the run ends: destroy, pause or keep.
- `--agent string` - Run a saved agent (name or id) instead of an ad hoc one.
- `--chat string` - Chat id; continues the chat if it has runs.
- `--computer string` - Computer to run in.
- `--continue` - Continue the most recent run on the target.
- `--file string` - Read the prompt from a file.
- `--harness string` - Harness: claude-code, codex, osa, opencode, pi, prime, kimi, mistral, hermes (default: the agent's, or claude-code).
- `--idempotency-key string` - Replay-safe key: the same key returns the same run.
- `--machine string` - Kind of new machine: sandbox or computer.
- `--max-time int` - Stop the run after this many seconds.
- `--model string` - Model for the harness (default: the harness default; see 'miosa connections harnesses HARNESS').
- `--new-chat` - Start a chat (a new chat id is generated and printed).
- `--new-machine` - Provision a machine for this run.
- `--no-follow` - Print the run id and return without waiting.
- `--notify-email` - Email you when the run finishes.
- `--notify-webhook string` - Webhook id to notify when the run finishes.
- `--reuse string` - New machine lifetime: run (one per run) or chat (one per --chat, files persist).
- `-s, --sandbox string` - Sandbox to run in (default: the current sandbox).
- `--size string` - Size of a new machine: micro, tiny, xs, small, quad, medium, large, xl.
- `--source string` - Label recorded on the run (max 40 characters).
- `--template string` - Template of a new machine.
- `--workspace string` - Workspace (slug or id) for a new machine.

### `miosa ssh`

Open an SSH session in a sandbox, or run a command over it.

```
miosa ssh [name|id] [-- <cmd> [args...]] [flags]
```

Connect to a sandbox with the system ssh client. miosa makes a one-time key,
asks the API for a short-lived certificate for it (15 minutes) that only this
sandbox accepts, and runs ssh through MIOSA's authenticated tunnel.
Where the
server has no certificate authority it authorizes the one-time key in the
sandbox instead.
The key, certificate and host file live in a private temporary
directory that is removed when ssh ends.
Nothing needs setting up in ~/.ssh.

With no command and a terminal you get a login shell.
Standard input is piped
through, so a script that is not on the sandbox yet runs without copying it:

```
  miosa ssh my-box -- bash -s < ./setup.sh
  cat ./setup.sh | miosa ssh my-box -- bash -s
  miosa ssh my-box < ./setup.sh          # no command: runs 'bash -s'
  miosa ssh my-box -- bash -lc "cd my-repo && npm test"

```
With several arguments after -- each one is quoted, so 'bash -lc "a && b"'
reaches the sandbox as written. miosa exits with the remote command's exit code.

When ssh or ssh-keygen is not installed, or with --api, the command runs over
the MIOSA API instead of an SSH connection: standard input is then read to the
end and sent with the command, so it is limited to 80KB, and the global
--timeout bounds the command (1-300 seconds, default 30).
Without a command and
with a terminal on stdin that mode opens 'miosa console'.

Flags:

- `--api` - Run over the MIOSA API instead of an SSH connection.
- `--cwd string` - Working directory, relative to the sandbox home directory.

### `miosa workspace`

Manage workspaces.

```
miosa workspace
```

Workspaces group machines, deployments and data inside your organization. <workspace> is a slug, name or id.

#### `miosa workspace activity`

Recent activity in a workspace.

```
miosa workspace activity <workspace>
```

#### `miosa workspace create`

Create a new workspace.

```
miosa workspace create <name>
```

#### `miosa workspace delete`

Delete a workspace (asks you to type its name).

```
miosa workspace delete <workspace> [flags]
```

Deletes the workspace.
On a terminal it shows the workspace and asks you to
type its name to confirm.
Off a terminal (scripts, CI) it refuses unless --yes
is given. <workspace> is its name, slug or id.

Flags:

- `-y, --yes` - Delete without the typed confirmation.

Examples:

```
miosa workspace delete acme
  miosa workspace delete acme --yes
```

#### `miosa workspace get`

Show a workspace.

```
miosa workspace get <workspace>
```

Aliases: `show`.

#### `miosa workspace inventory`

Everything a workspace contains.

```
miosa workspace inventory <workspace>
```

#### `miosa workspace list`

List workspaces.

```
miosa workspace list
```

Aliases: `ls`.

#### `miosa workspace members`

List the people in a workspace.

```
miosa workspace members <workspace>
```

#### `miosa workspace stats`

Counts of machines, deployments and databases.

```
miosa workspace stats <workspace>
```

#### `miosa workspace usage`

Spend and runtime in a workspace.

```
miosa workspace usage <workspace>
```

#### `miosa workspace use`

Make a workspace the default for this profile.

```
miosa workspace use <workspace>
```

Stores the workspace slug as default_workspace in the active profile.
The workspace must exist.
