# miosa command reference

Generated by `miosa __docs`; do not edit by hand.
Regenerate with `make docs`.

## Global flags

- `--api-key string` - API key (overrides MIOSA_API_KEY and config).
- `--api-url string` - API base URL (overrides MIOSA_BASE_URL and config).
- `--json` - Print machine-readable JSON (same as --output json).
- `--no-update-notice` - Silence the new-version notice (env: MIOSA_NO_UPDATE_NOTICE=1).
- `--org string` - Organization to bill for this command: id, slug or name (env MIOSA_ORG).
- `-o, --output string` - Output format: text or json. (default `text`)
- `--profile string` - Config profile to use (env: MIOSA_PROFILE).
- `-q, --quiet` - Suppress informational output.
- `--retries int` - Retries on 429 and transient 5xx errors (default 3, env: MIOSA_RETRIES). (default `-1`)
- `--timeout int` - Request timeout in seconds (0 = no timeout); for exec and ssh also the command timeout, 1-300. (default `60`)

### `miosa agent`

Define, version and run agents.

```
miosa agent
```

An agent is a saved, versioned definition: harness, model, instructions, the
machine it runs on, and what it may do.
Runs always use your own model
connections ('miosa connections add models'). <agent> is a name or an id.

```
  miosa agent new reviewer --harness claude-code --instructions-file review.md
  miosa agent publish reviewer --file config.yaml
  miosa agent diff reviewer 2 3
  miosa agent run reviewer "review PR 42" --sandbox my-box
  miosa agent harnesses
```

Aliases: `agents`.

#### `miosa agent new`

```

```

```

  miosa agent new builder -f builder.yaml --overdrive

Flags:

- `-f, --file string` - Configuration as YAML or JSON (the version's `configuration` object).
- `--harness string` - Harness: claude-code, codex, osa or custom.
- `--instructions string` - Instructions text.
- `--instructions-file string` - Read the instructions from a file.
- `--model string` - Model.
- `--overdrive` - Run the harness without approval prompts (stored on the version).
- `--project-id string` - Project id.
- `--timeout-sec int` - Run time limit in seconds (execution.timeout_seconds).
- `--workspace-id string` - Workspace id.

#### `miosa agent publish`

Publish a new immutable version.

```
miosa agent publish <agent> [flags]
```

Publish a new version of an agent from --file and/or flags.
The full configuration
is validated and fingerprinted; a version never changes after publication, so
a run can always prove what it ran.
Runs started before keep their version.

Flags:

- `-f, --file string` - Configuration as YAML or JSON (the version's `configuration` object).
- `--harness string` - Harness: claude-code, codex, osa or custom.
- `--instructions string` - Instructions text.
- `--instructions-file string` - Read the instructions from a file.
- `--model string` - Model.
- `--overdrive` - Run the harness without approval prompts (stored on the version).
- `--timeout-sec int` - Run time limit in seconds (execution.timeout_seconds).

### `miosa api`

Make an authenticated API request.

```
miosa api [METHOD] <path> [flags]
```

Send a request to the MIOSA API with your stored credentials and print the
response body.
The path is relative to the API base URL (/api/v1).
Use it for
anything the CLI has no command for yet.

The method defaults to GET, or POST when --data is given. --data takes a JSON
string, @file to read a file, or - to read standard input.
A failing status
exits non-zero (see 'miosa --help' for exit codes) and still prints the body.

```
  miosa api /credits/balance
  miosa api GET /sandboxes/my-box/ports
  miosa api POST /webhooks -d '{"url":"https://example.com/hook","events":["sandbox.ready"]}'
  miosa api PATCH /sandboxes/my-box/tags -d @tags.json
  echo '{"name":"x"}' | miosa api POST /workspaces -d -
```

Flags:

- `-d, --data string` - Request body: JSON, @file, or - for stdin.
- `-H, --header stringArray` - Extra header, 'Name: value' (repeatable).
- `-i, --include` - Print the status line and response headers first.
- `-X, --method string` - HTTP method (default GET, or POST with --data).

### `miosa api-key`

Create and manage API keys.

```
miosa api-key
```

API keys let scripts, CI and other programs call MIOSA.
A key is shown once, at
creation and rotation; store it right away.
A key acts as your organization
with the permissions you give it.

```
  miosa api-key create ci --preset ci --expires-in 90
  miosa api-key create reviewer --scope agents:read --scope agents:run
  miosa api-key list
  miosa api-key rotate <id>
  miosa api-key rm <id>

```
The key goes to standard output on create, so you can capture it:
```
  KEY=$(miosa api-key create ci --preset ci --quiet-key)
```

Aliases: `api-keys`, `keys`.

#### `miosa api-key create`

Create a key.

```
miosa api-key create <name> [flags]
```

Create an API key.
With no --scope or --preset the key gets the default set of
scopes.
Presets: read-only (every :read scope), ci (sandboxes, deployments,
previews), agent (run agents on sandboxes), cli (what the miosa CLI uses day to
day, including connections). 'miosa api-key presets' lists them.
Scope names look like sandboxes:exec
or agents:run; see 'miosa api-key list --json' for what existing keys hold.

The secret is printed once. --quiet-key prints only the secret.

Flags:

- `--allowed-ip stringArray` - Only accept requests from this IP or CIDR (repeatable).
- `--expires-in int` - Expire after this many days (default: never).
- `--preset string` - Permission preset: read-only, ci, agent or cli.
- `--quiet-key` - Print only the secret.
- `--rate-limit int` - Requests per minute for this key.
- `--scope stringArray` - A scope to grant, for example sandboxes:exec (repeatable).
- `--workspace-id string` - Bind the key to one workspace.

#### `miosa api-key list`

List keys (revoked ones hidden unless --all).

```

Aliases: `ls`.

Flags:

- `--all` - Include revoked keys.

### `miosa batch`

Create many sandboxes in one request.

```
miosa batch
```

A batch asks for N identical sandboxes and creates them with bounded
concurrency.
The call returns at once with a batch id; 'status' and 'watch'
show how many are up, and 'items' lists the sandboxes.
Quota, credit and
placement apply to every sandbox as for a single 'miosa create'.

```
  miosa batch new --count 50 --size small --name-prefix ci --wait
  miosa batch status <batch>
  miosa batch items <batch>
  miosa batch cancel <batch>
```

Aliases: `batches`.

#### `miosa batch cancel`

Stop creating the sandboxes still pending.

```
miosa batch cancel <batch>
```

Sandboxes already created are left alone; destroy them with 'miosa destroy'.
A batch that has finished cannot be canceled.

#### `miosa batch items`

List the sandboxes of a batch.

```
miosa batch items <batch> [flags]
```

Flags:

- `--limit int` - How many to show.

#### `miosa batch new`

Create a batch of identical sandboxes.

```
miosa batch new [flags]
```

Creates --count sandboxes (1 or more; the server states the maximum for your
plan) with at most --concurrency creating at once.
Prints the batch id.
With --wait the command blocks until the batch has settled and exits non-zero
if any sandbox failed.

```
  miosa batch new --count 20 --template nextjs --name-prefix demo --ttl 2h --wait
```

Flags:

- `--concurrency int` - How many to create at once (default: the server's).
- `--count int` - How many sandboxes to create.
- `--idle-timeout string` - Idle timeout of each sandbox, for example 15m.
- `--name-prefix string` - Prefix for the sandbox names, numbered from 1.
- `--region string` - Region.
- `--size string` - Sandbox size, as for 'miosa create'.
- `--tag stringArray` - Tag KEY=VALUE for every sandbox (repeatable).
- `--template string` - Sandbox template (default miosa-sandbox).
- `--ttl string` - Time to live of each sandbox, for example 2h.
- `--wait` - Wait until the batch has settled.
- `--wait-timeout duration` - How long --wait may take. (default `15m0s`)
- `--workspace string` - Workspace slug.

#### `miosa batch status`

Show how a batch is going.

```
miosa batch status <batch>
```

Aliases: `get`.

#### `miosa batch watch`

Follow a batch until it settles.

```
miosa batch watch <batch> [flags]
```

Prints a progress line each time the batch changes and exits when it has
settled: 0 when every sandbox came up, non-zero when any failed or the batch was
canceled.

Flags:

- `--timeout duration` - Give up after this long. (default `15m0s`)

### `miosa catalog`

Show canonical compute products, templates, sizes, and readiness.

```
miosa catalog [flags]
```

Show the canonical MIOSA compute catalog.

Use this before creating resources so you can choose the right product lane
(sandbox, computer, docker_deploy_host), template, size, and fast-readiness

Readiness states are fast_ready, cold_boot_only, and missing.

Flags:

### `miosa chat`

Chats with an agent that remembers.

```
miosa chat
```

A chat is a series of runs that share a chat id: each follow-up resumes the
harness's own session on the same machine, so the agent keeps its context.

```
  miosa chat start --sandbox my-box      # interactive; prints the chat id
  miosa chat list
  miosa chat show 3f0c...
  miosa prompt --chat 3f0c... "and add tests"
```

#### `miosa chat compact`

Compact the agent's context so the chat can go on.

```
miosa chat compact <chat-id> [flags]
```

Starts a run in the same chat, on the same machine, that compacts the harness's

### `miosa create`

Create a new sandbox.

```
miosa create [name] [flags]
```

Provision a new MIOSA sandbox.

If no name is provided, one is generated automatically.

Examples:
```
  miosa create my-box
  miosa create my-box --size medium --template miosa-sandbox
  miosa create --size large
  miosa create my-box --env staging
  miosa create my-box --no-env
  miosa create my-box --setup-file ./setup.sh

- `--meta stringArray` - Metadata, KEY=VALUE (repeatable).
- `--no-env` - Pass nothing of yours to the sandbox (safe to hand to third parties).
- `--setup-file string` - Shell script (UTF-8, max 64KB) run in the background once the sandbox is ready.
- `--size string` - Sandbox size: micro, tiny, xs, small, quad, medium, large, xl. (default `small`)
- `--template string` - Sandbox template, for example miosa-sandbox, nextjs, fastapi, or hono. (default `miosa-sandbox`)
- `--ttl string` - Time to live: seconds, 90m, 2h or 2d (default: the plan's).
- `--wait` - Wait until the sandbox is ready for commands.
- `--wait-timeout duration` - How long --wait may take. (default `3m0s`)
- `--workspace string` - Workspace slug to assign the sandbox to.

### `miosa exec`

Execute a command in a sandbox.

```
miosa exec [name|id] -- <cmd> [args...] [flags]
```

Run a command inside a sandbox and print its output. miosa exits with the
remote command's exit code, so it drops straight into scripts and CI.

The -- separator is required before the command and its arguments.

--cwd sets the working directory, relative to the sandbox home directory (or
absolute).
The global --timeout also bounds the command: seconds, 1-300, default
30 when not given, 0 means the 300 second maximum.

A sandbox that is still starting refuses commands; exec retries with backoff
until it is ready (up to 90 seconds).

Examples:
```
  miosa exec my-box -- echo hello
  miosa exec -- ls -la /home      # uses current sandbox
  miosa exec my-box --cwd my-repo --timeout 120 -- npm run build
  miosa exec my-box -- bash -c 'for i in 1 2 3; do echo $i; done'
```

Flags:

- `--cwd string` - Working directory, relative to the sandbox home directory.

### `miosa prompt`

- `--machine string` - Kind of new machine: sandbox or computer.
- `--max-time int` - Stop the run after this many seconds.
- `--model string` - Model for the harness (default: the harness default).
- `--new-chat` - Start a chat (a new chat id is generated and printed).
- `--new-machine` - Provision a machine for this run.
- `--no-follow` - Print the run id and return without waiting.
- `--notify-email` - Email you when the run finishes.
- `--notify-webhook string` - Webhook id to notify when the run finishes.
- `--reuse string` - New machine lifetime: run (one per run) or chat (one per --chat, files persist).

### `miosa snapshot`

it stays after the machine is gone and is never part of history.

```

### `miosa ssh`

Open an SSH session in a sandbox, or run a command over it.

```
miosa ssh [name|id] [-- <cmd> [args...]] [flags]
```

Connect to a sandbox with the system ssh client. miosa makes a one-time key,
asks the API for a short-lived certificate for it (15 minutes) that only this
sandbox accepts, and runs ssh through MIOSA's authenticated tunnel.
Where the
server has no certificate authority it authorizes the one-time key in the
sandbox instead.
The key, certificate and host file live in a private temporary
directory that is removed when ssh ends.
Nothing needs setting up in ~/.ssh.

With no command and a terminal you get a login shell.
Standard input is piped
through, so a script that is not on the sandbox yet runs without copying it:

```
  miosa ssh my-box -- bash -s < ./setup.sh
  cat ./setup.sh | miosa ssh my-box -- bash -s
  miosa ssh my-box < ./setup.sh          # no command: runs 'bash -s'
  miosa ssh my-box -- bash -lc "cd my-repo && npm test"

```
With several arguments after -- each one is quoted, so 'bash -lc "a && b"'
reaches the sandbox as written. miosa exits with the remote command's exit code.

When ssh or ssh-keygen is not installed, or with --api, the command runs over
the MIOSA API instead of an SSH connection: standard input is then read to the
end and sent with the command, so it is limited to 80KB, and the global
--timeout bounds the command (1-300 seconds, default 30).
Without a command and
with a terminal on stdin that mode opens 'miosa console'.

Flags:

- `--api` - Run over the MIOSA API instead of an SSH connection.
- `--cwd string` - Working directory, relative to the sandbox home directory.

### `miosa webhook`
